# setup-supabase: 가입 직후 로그인 상태, 상태를 반영하는 Header, profiles 기본 컬럼

대상: 프로젝트 로컬 스킬 `setup-supabase` (`.claude/skills/setup-supabase/`, `.agents/skills/setup-supabase/`). `skills-lock.json`에 없는 로컬 스킬이므로 이 저장소에서 직접 고친다.

연결된 결정 계약:
- [ui-composition](../../decisions/ui-composition.md) — Header를 공통 shell에 두고 공식 shadcn component로 구성하는 근거. Header의 위치·구성 규칙은 이 계약을 따른다.

## 배경 (확인한 원인)

- **가입 후 로그인을 한 번 더 함**: 스킬이 시작점으로 지정한 Supabase UI Library `password-based-auth-nextjs` 블록의 `sign-up-form`은 `signUp()` 성공 시 세션 유무와 관계없이 `/auth/sign-up-success`("이메일 확인 후 로그인하세요")로 이동한다. 이메일 인증을 끄면 `signUp()`이 세션을 돌려주는데도 이를 쓰지 않는다. 스킬은 인증이 꺼진 경우의 가입 후 목적지를 정하지 않았다. (2026-11-18, 레지스트리 `https://supabase.com/ui/r/password-based-auth-nextjs.json`에서 확인)
- **Header가 상태를 반영하지 않음**: 스킬에 Header 규칙이 없다. 또 블록의 로그인·로그아웃은 `router.push()`만 호출한다. 설치된 Next.js 16.4.5 문서상 레이아웃은 이동 시 다시 렌더링되지 않으므로, 레이아웃에서 그린 Header는 인증 상태가 바뀌어도 이전 상태로 남는다.
- **profiles에 created_at, updated_at, email이 없음**: 스킬은 공식 User Management 패턴과 "표시 이름 필드 하나만 추가"를 지시한다. 공식 예시(`id`, `first_name`, `last_name`)에 타임스탬프와 이메일이 없다.

## 사용자에게 보이는 결과

스킬을 이메일/비밀번호 Auth로 실행해 만들어진 앱에서:

1. 이메일 인증이 꺼져 있으면, 가입하자마자 로그인된 상태가 되고 로그인 후와 같은 목적지로 이동한다. 로그인 화면을 다시 거치지 않는다.
2. Header가 현재 인증 상태를 보여 준다. 로그아웃 상태에서는 `로그인` 링크 하나, 로그인 상태에서는 `설정` 링크와 `로그아웃` 버튼.
3. 가입·로그인·로그아웃 직후 새로고침 없이 Header가 바뀐다.
4. profile에 생성 시각, 수정 시각, 이메일이 함께 저장되고, `/settings`에서 이메일을 읽기 전용으로 볼 수 있다.

## 승인된 범위

- 이메일/비밀번호 경로의 가입 후 흐름
- 인증 상태를 반영하는 Header (이메일/비밀번호와 Google 경로 공통)
- profiles 테이블의 `created_at`, `updated_at`, `email` 컬럼과 그 값의 수명 규칙
- 스킬의 검증 항목에 위 동작 추가

## 수용 기준

스킬을 실행해 만든 앱에서 아래가 실제 브라우저로 확인되어야 한다.

- AC1. 이메일 인증이 꺼진 상태에서 새 이메일로 가입하면, 로그인 화면이나 가입 완료 안내 화면을 거치지 않고 로그인 후와 같은 목적지(`next`가 있으면 그곳, 없으면 앱 기본 목적지)에 로그인된 상태로 도착한다.
- AC2. 이메일 인증이 켜진 상태에서는 가입 후 이메일 확인 안내가 보이고, 확인 링크를 거친 뒤 로그인된다(기존 동작 유지).
- AC3. 로그아웃 상태의 모든 페이지 Header에는 `로그인` 링크만 있고 `설정`·`로그아웃`은 없다.
- AC4. 로그인 상태의 모든 페이지 Header에는 `설정` 링크와 `로그아웃` 버튼이 있고 `로그인`은 없다.
- AC5. 가입, 로그인, 로그아웃 각각의 직후, 수동 새로고침 없이 Header가 AC3/AC4의 상태로 바뀐다.
- AC6. Header의 `로그아웃`을 누르면 로그아웃되고, 이후 `/settings`에 접근할 수 없다.
- AC7. 새 사용자의 profile 행에 `created_at`, `updated_at`, `email`이 채워지며, 가입 직후 `created_at`과 `updated_at`이 같고 `email`은 Auth 사용자 이메일과 같다.
- AC8. `/settings`에서 표시 이름을 수정하면 `updated_at`이 수정 시각으로 바뀌고 `created_at`은 그대로다. 앱 코드가 아니라 DB가 이 갱신을 보장한다.
- AC9. `/settings`에 이메일이 읽기 전용으로 보이며, 수정 가능한 필드는 표시 이름 하나뿐이다.
- AC10. 기존 owner-only 경계(다른 사용자·비로그인 사용자가 profile을 읽거나 수정할 수 없음)가 그대로 유지된다.

스킬 동작은 실행마다 달라질 수 있으므로 eval로 증명한다.

- 지표: 스킬 실행 1회로 만든 앱이 AC1, AC3–AC10을 모두 통과하는 비율
- 목표: 3회 중 3회 통과
- 케이스 출처: `main` 기준 깨끗한 템플릿 체크아웃을 매 실행 새로 만든 것. 이메일/비밀번호, 이메일 인증 끔 선택. 스킬 본문을 쓰는 데 사용한 체크아웃은 쓰지 않는다.

## 확정된 제약과 근거

- 가입 후 목적지는 로그인 후 목적지와 같다. 가입과 로그인이 같은 곳에 도착해야 수강생이 흐름을 하나로 이해한다. (사용자 확정)
- Header 구성은 로그아웃 시 `로그인` 하나, 로그인 시 `설정` + `로그아웃`. 가입 링크는 로그인 화면에 이미 있다. 로그아웃이 Header에 있으면 어디서나 나갈 수 있고 검증이 쉽다. (사용자 확정)
- `email`은 가입 시 한 번만 복사하고, 이후 Auth 이메일이 바뀌어도 동기화하지 않는다. 스킬은 이메일 변경 기능을 만들지 않으므로 앱 안에서 어긋날 일이 없고, 동기화 트리거는 수강생이 이해할 DB 장치만 늘린다. (사용자 확정)
- `updated_at` 갱신은 DB가 보장한다. 앱 코드가 값을 넣는 것에 의존하지 않는다. (사용자 확정)
- 스킬을 고칠 때 `.claude/skills/setup-supabase`와 `.agents/skills/setup-supabase`를 symlink 없이 같은 내용으로 함께 바꾼다. (AGENTS.md 프로젝트 스킬 설치 방식)
- 스킬의 기존 원칙은 유지한다. 명령어·SQL·프레임워크 코드 조각·대시보드 클릭 경로를 스킬 본문에 복사하지 않고, 원하는 동작과 검증 항목으로 기술한다.

## 가정 (바꿀 수 있음)

- 이미 profiles 테이블이 있는 프로젝트에서 스킬을 재개하면, 없는 컬럼만 추가하고 기존 행의 `email`은 Auth 사용자 이메일로, 타임스탬프는 적용 시점으로 채운다.
- Header 문구는 앱의 기존 언어를 따른다. 템플릿 기본값은 한국어(`로그인`, `설정`, `로그아웃`).
- Google 경로에서도 Header 규칙(AC3–AC6)과 profiles 컬럼(AC7–AC9)이 같이 적용된다. Google 경로의 가입 후 흐름은 이번에 바꾸지 않는다.

## 범위 밖과 이유

- 이메일 변경, 비밀번호 재설정, 계정 삭제 — 스킬의 기존 제외 목록 유지.
- Auth 이메일 변경 시 profiles `email` 동기화 — 위 제약 참고.
- 아바타, 사용자 메뉴 드롭다운, Header의 사용자 이름 표시 — 요청되지 않음.
- 보안 하드닝·엣지케이스 방어 — AGENTS.md 검증·리뷰 예산.

## 남은 위험

- 대시보드나 Admin API로 Auth 이메일을 직접 바꾸면 profiles `email`과 어긋난다. 이메일 변경 기능을 추가하는 작업이 생기면 동기화를 다시 정한다.
- 공식 UI 블록이 업데이트되어 가입·로그인 후 동작이나 파일 구성이 바뀌면, 스킬의 적용 지시를 다시 확인해야 한다.
